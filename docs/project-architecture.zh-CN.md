# Sigilora 符号字体项目设计

## 1. 背景

Sigilora 是一套面向游戏文本的符号字体项目。它使用 OpenType ligature 将游戏社区已经成熟的文本表示转换为彩色符号，并通过 COLR/CPAL 在文本行内直接渲染这些符号。

项目的核心价值不是提供普通 icon font，而是让符号继续保留文本身份：

- 原始内容可以复制、搜索和存储
- 未加载字体时可以退化为游戏已有的文本表示
- 加载对应游戏字体后，文本表示自动呈现为彩色符号
- 不同游戏可以保留各自已有的符号语法

Sigilora 是独立于当前网站发布的中立项目。当前网站只是它的一个消费者。

## 2. 目标

Sigilora 的目标是：

1. 为具有成熟符号文本表示的游戏提供可嵌入文本的彩色符号字体
2. 允许每个游戏独立维护字体内容、COLR 版本和字体版本
3. 使用统一仓库、构建流程和发布入口降低多游戏维护成本
4. 同时支持 Web 使用、桌面安装和公开在线预览
5. 让当前网站和其他消费者通过稳定发布产物集成，而不是依赖字体源码仓库

## 3. 非目标

当前设计不包含以下目标：

- 不建立跨游戏统一的符号文本语法
- 不把所有游戏符号合并进同一个字体文件
- 不要求一个页面通过单次网络请求加载多个游戏字体
- 不为不同游戏创建独立代码仓库
- 不在初始阶段建立专属 GitHub 组织
- 不在初始阶段实现多个可切换的字体构建后端
- 不在本设计中确定当前网站的自动配置 manifest 协议
- 不在本设计中完成第三方素材的逐项授权审计

## 4. 项目身份与命名

### 4.1 总名称

项目总名称为 **Sigilora**。

名称保留 `sigil` 的现代词根，并通过幻想化派生形成类似游戏世界中符号体系或魔法学派的感觉。项目接受互联网上已经存在同名使用这一事实，不再继续更换名称。

### 4.2 游戏字体命名

所有游戏字体统一使用以下命名层级：

- 字体家族：`Sigilora <Game>`
- PostScript/文件标识：使用稳定的 ASCII 游戏标识
- Web 产物：按游戏分别生成 CSS 和 WOFF2
- 桌面产物：按游戏分别生成 TTF

游戏显示名称与稳定游戏标识应分离。显示名称用于字体家族和文档，稳定标识用于目录、文件、manifest 和导出路径。

## 5. 仓库与项目边界

### 5.1 独立仓库

Sigilora 使用独立仓库，不放入当前网站仓库，也不作为当前网站的 Git submodule。

独立仓库初期可以托管在现有组织或个人账号下。只有在出现多个 Sigilora 仓库、多名维护者或独立权限管理需求后，才建立专属 GitHub 组织。

### 5.2 当前网站的集成边界

当前网站只消费已发布的 Sigilora 产物，不读取或构建字体源码。

允许当前网站通过脚本感知和配置字体，但脚本应依赖 npm 包公开的机器接口，而不是依赖 Sigilora 仓库目录结构。根 manifest 的具体结构延后到集成设计阶段确定。

### 5.3 仓库逻辑结构

Sigilora 仓库以字体工程为中心，而不是以 npm 包或官网为中心。主要逻辑组件包括：

```text
sigilora/
├── pyproject.toml
├── src/sigilora_build/       # Python 构建与验证逻辑
├── fonts/<game>/             # 各游戏的规范源数据
├── packages/fonts/           # @sigilora/fonts 发布目录
├── website/                  # Nuxt 官网、文档与 playground
└── tests/                    # 字体结构、映射和塑形验证
```

上图表达组件边界；独立仓库创建时可以根据最终 workspace 约定调整官网目录名，但不得改变以下职责：

- Python 工具链负责生成和验证字体
- `packages/fonts/` 只负责 npm 消费产物
- 官网通过公开产物消费字体，不拥有字体源码

## 6. 字体划分与文本行为

### 6.1 按游戏拆分字体

每个游戏生成独立字体文件。一个典型页面通常只使用一个游戏字体，因此不提供跨游戏合并字体，也不把“多个字体压缩成一个网络请求”作为设计目标。

按游戏拆分可以：

- 隔离不同游戏之间重叠的文本表示
- 避免单个字体持续膨胀
- 允许不同游戏独立选择 COLR 版本
- 允许每个游戏独立维护字体版本

### 6.2 ligature 协议

每个游戏字体优先采用该游戏社区已经成熟的原生符号文本表示，不发明 Sigilora 跨游戏统一语法。

只要应用了对应的 Sigilora 字体，匹配文本默认通过标准 `liga` 特性转换为符号。代码块或不应转换的区域由消费方不应用该字体，或显式关闭 ligature。

已知浏览器限制：在 WebKit 浏览器（macOS 与 iOS 的 Safari）中，输入包含 ASCII 连字符（`-`，U+002D）且其后紧跟字母的 `liga` 连字不会被应用，因为 WebKit 会在该位置切开 shaping run。对 Magic 字体而言，这影响 `[-X]` 与 `[-N]`。当前字体未为这两个符号映射替代输入字符。这是整形引擎行为，不是字体缺陷，也不会被基于 HarfBuzz 的验证捕获。

### 6.3 COLR 版本

COLR 版本是每个字体的独立构建属性，不是项目级全局约束：

- 当前已实现且只需要纯色叠层的字体使用 COLRv0
- PTCG 等需要渐变、透明度或复杂变换的字体可以使用 COLRv1
- 不为统一技术栈而提前升级不需要 COLRv1 的字体

## 7. 源数据与构建

### 7.1 规范源数据

每个游戏的规范源数据包括：

- 规范化 SVG
- ligature 文本映射
- 字形标识和显示信息
- 字体内部版本
- COLR 目标版本
- 素材来源与授权记录

规范化 SVG 与映射数据是项目的长期源数据。构建工具配置不是公共契约。

### 7.2 当前构建后端

当前使用 `nanoemoji` 生成字体。`nanoemoji` 作为 `sigilora_build` 内部的构建后端存在，不直接暴露给 npm 消费者或官网。

项目只在架构上保留替换构建后端的能力，初期只实现 nanoemoji 后端，不建设插件式多构建器系统。未来可以改用 fontTools、自定义 Python 管线或 UFO/fontmake 工作流，只要保持源数据语义、产物契约和验证结果一致。

### 7.3 构建产物

同一份源数据生成：

- Web 使用的 WOFF2
- 桌面安装使用的 TTF
- CSS `@font-face` 定义
- 字体和符号元数据
- specimen 所需数据

不为了格式对称而额外生成内容等价的 OTF。

## 8. npm 分发与版本

### 8.1 单包分发

所有游戏字体通过一个 npm 包发布：

```text
@sigilora/fonts
```

包内按游戏提供独立 CSS、WOFF2 和元数据。消费方只导入需要的游戏入口，浏览器也只请求实际引用的 WOFF2。npm 安装时包含其他小型字体文件是可接受的维护成本。

npm 包只包含消费产物、类型声明和授权信息，不包含 SVG 源文件、Python 构建实现或测试代码。

### 8.2 双层版本模型

npm 包版本与字体版本相互独立。

npm 包版本只描述发布容器和公共接口：

- Major：导出路径或公共机器接口发生不兼容变化
- Minor：新增游戏字体
- Patch：更新任意现有字体产物

每个游戏字体在 OpenType 元数据和自身元数据中维护独立 SemVer：

- Major：删除 ligature、改变既有文本映射或移除字形
- Minor：新增符号、ligature 或兼容别名
- Patch：不改变映射的视觉修正、轮廓优化或元数据修复

某个字体升级 Major 不要求 npm 包同步升级 Major。消费者需要通过字体元数据判断具体游戏字体的兼容性变化。

### 8.3 默认消费方式

默认文档推荐安装 npm 包并由消费方自托管字体。支持 npm 的公共 CDN 可以作为便捷选项，但不是默认部署方式。

## 9. GitHub Release

每次发布创建一个与 npm 包版本和 Git tag 对齐的 GitHub Release。

Release 包含：

- `Sigilora-Fonts-<package-version>.zip`：全部字体文件（TTF 和 WOFF2）的完整快照
- `Sigilora-<Game>-<font-version>.zip`：每个游戏字体的独立下载包（TTF 和 WOFF2）
- `SHA256SUMS`：Release 资产校验值

每个 Release 重新附带全部游戏的独立 ZIP，即使某些字体在本次发布中没有变化。字体体积较小，完整快照比节省少量存储更重要。

Release ZIP 同时包含 TTF 和 WOFF2 及许可证信息：TTF 用于桌面安装，WOFF2 用于 Web 直接自托管。通过 npm 的 Web 消费仍使用包内按游戏提供的 CSS 和 WOFF2。这一实践与 Noto Color Emoji、Material Symbols、Font Awesome 等常见开源字体项目一致。

## 10. 验证与质量门槛

发布前必须自动完成以下阻断验证：

1. OpenType、TTF 和 WOFF2 文件结构有效
2. 所有声明的 ligature 都能通过 HarfBuzz 正确塑形
3. 映射无重复、无缺失 SVG、无未引用字形
4. COLR/CPAL 表符合该字体声明的 v0 或 v1
5. TTF 与 WOFF2 的字形、映射和字体内部版本一致

项目同时为每个游戏自动生成 specimen 页面，展示：

- 原始文本与 ligature 渲染结果
- 全部符号和色板
- 多种字号下的行内效果
- 可复制的输入文本和使用代码

初期不使用跨平台像素级快照作为发布阻断条件，因为彩色字体渲染会受到浏览器和操作系统影响。结构、映射和塑形验证必须阻断发布，视觉检查通过公开 specimen 完成。

## 11. 官网与文档

### 11.1 技术方向

Sigilora 官网使用 Nuxt 4，既是公开官网和文档站，也是字体的交互式 specimen/playground。

核心页面至少包括：

- 项目介绍与安装入口
- 支持游戏和字体版本总览
- 每个游戏的字体详情与完整符号表
- 实时文本输入、字体切换和 ligature 预览
- CSS、npm 和桌面安装文档
- 版本记录与兼容性说明

### 11.2 多语言

官网沿用当前项目的动态 i18n 行为模式：

- 使用 `@nuxtjs/i18n`
- 路由采用 `no_prefix`
- 通过浏览器语言和 Cookie 确定初始语言
- 用户语言设置变化时动态调用 `setLocale`
- Nuxt UI locale 与站点语言同步

Sigilora 只复用这一行为模式，不依赖当前仓库的 `@tcg-cards/*` 配置或 UI 包。

内容分工如下：

- 导航、按钮和 playground 界面文案使用 `vue-i18n`
- 指南、字体说明和版本记录使用按语言组织的 Nuxt Content Markdown

## 12. 授权边界

字体图形可能来自自行重绘、公开来源和购买的第三方绘制。每个游戏必须记录素材来源和许可依据。

本设计不假设普通商业使用许可天然允许：

- 将图形转换为字体字形
- 随字体二进制公开分发
- 允许用户安装、嵌入和再分发字体
- 使用 OFL 或其他许可证再次授权

具体素材审计和最终许可证组合单独设计。在审计完成前，不把所有字体统一声明为 OFL，也不对第三方素材的再分发权作推定。

## 13. 延后事项

以下事项已经明确延后，不阻塞当前项目边界成立：

1. `@sigilora/fonts` 根 manifest 的字段、schema 和稳定性策略
2. 当前网站自动读取 manifest 并生成字体配置的脚本协议
3. 各游戏素材的逐项授权审计和最终许可证组合
4. Sigilora 专属 GitHub 组织的建立时机
5. 除 nanoemoji 外的其他构建后端
6. 像素级视觉回归测试

这些事项需要在进入对应实现阶段前分别确认，不应由实现者自行补全设计。
